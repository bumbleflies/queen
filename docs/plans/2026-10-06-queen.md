# queen Implementation Plan

> **For Claude:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build `bumbleflies/queen` — the finance & operations app for **all** of bumbleflies (consulting, trainings, LeagueSphere licences) at `queen.bumbleflies.de`. It replaces the ledger Sheet `1yLKEp-dQw7Etz6n-XVoRi8nPXGhLqFcDVcTN6nVrLlk` ("Debitoren und Ausgangsrechnungen (gestellt)") with full invoice CRUD, PDF + Drive filing, and Firefly/GLS auto-reconcile. It is designed to become the superset of `leagues.finance` invoicing.

**Architecture:** Standalone TypeScript app (React 19 + Vite client, Express + tRPC server, MongoDB as sole ledger). **No dependency on LeagueSphere MySQL.** Domain-specific origins (league offers, seasons) are attached as optional `source` metadata, never as required foreign keys. queen is the **authority for customer numbers and invoice numbers**; `leagues.finance` becomes a client of queen's service API instead of writing to the Sheet. Bank data comes from Firefly III over its REST API; reconcile runs daily via Ofelia after the 06:00 GLS import.

**Tech Stack:** React 19, Vite, tRPC 11, Express, tsx, Mongoose 9, valkey + Bull, pdfkit, googleapis (Drive), Firefly III API v1, Docker, Traefik, Ofelia.

## Decisions (confirm or veto before Task 1)

| # | Decision | Why |
|---|----------|-----|
| D1 | Generic invoice lines (`description, quantity, unitNet, vatRate`), no league pricing in the core | The Sheet holds consulting, training and licence invoices; league pricing stays in leagues.finance |
| D2 | queen owns `customerNumber` + `invoiceNumber` allocation; leagues.finance calls `ext.invoices.create` | Today both leagues.finance and the Sheet allocate numbers → collisions once two apps write |
| D3 | Issued invoices are never deleted or reopened. Correction = **Stornorechnung** (credit note, own number, negative lines, `cancels: <invoiceId>`) | GoBD: issued numbers must stay gap-free and traceable |
| D4 | Service lives in `container/finance/docker-compose.yml` next to Firefly | Firefly's `backend` network is `internal` and project-scoped; same project = `http://firefly:8080` just works |
| D5 | Repo `bumbleflies/queen` is **public**; no customer data in git (fixtures anonymised, secrets in container git-crypt) | Code is generic; data lives only in Mongo/Drive |
| D6 | Statuses `draft → sent → paid`, `sent → canceled` (via credit note); `overdue` is computed. Sheet `open` maps to `sent` | Same vocabulary as leagues.finance |
| D7 | Money stored as **integer cents** everywhere | Avoid float drift in matching and sums |

## Facts from the Sheet (drive the data model + migration)

- **Tabs:** `clientData A:D` (clientId, clientName, standardInvoiceAddress, clientDomain) · `invoiceData A:O` (invoiceId, clientId, invoiceAddress, invoiceName, invoiceDate `DD.MM.YYYY`, jobPeriod, invoiceCurrency `€`, paymentTerm, state, finalInvoiceUrl, netSum, grossSum, vatSum, invoicePdfGenerationUrl, nameTemplate) · `invoicePositions A:J` (invoiceId, position, description, quantity, net, vat, netSum, vatAmount, grossSum, jobPeriod) · `const` (`nextInvoiceId` legacy counter) · `invoiceStates` (draft, open, paid, overdue, canceled).
- Clients `10001–10015`: consulting customers **and** league associations (10007, 10009–10014 overlap with leagues.finance `Association.customerNumber`).
- **Legacy invoice number `1001`** does not match `YYYYMMDD-NN`.
- Invoice number date ≠ invoice date (e.g. `20250106-01` dated 03.11.2025; `20250821-01` dated 29.01.2026). The number is allocated at draft creation, the date is set on issue.
- `position` is hierarchical text (`1`, `1.1`, `3.2`), not an int.
- Discounts are **negative lines** (`Nachlass Reisekosten 25%  -100,00 €`), not a discount field.
- VAT varies per line: `16%` (2020), `19%`, `0%` with a legal note (`§ 4 Nr. 21 a) bb) UStG steuerbefreit…`).
- `paymentTerm` varies: 14 (until 2022) and 30.
- `jobPeriod` is inconsistently padded (`5.2025` vs `05.2025`).
- `finalInvoiceUrl` is a Drive **file name** (sometimes prefixed `Gebucht - `), not a URL. `nameTemplate` = `YYYY-MM.<invoiceId> - <clientName> <clientId> - <invoiceName>.pdf`.
- Number formats are German (`1.600,00 €`, `9329,6`).
- Payment reference printed on PDFs (leagues.finance `PdfService.ts:427`): `Verwendungszweck: <customerNumber>-<invoiceNumber>`. Legacy invoices had no fixed reference.

## Data model (Mongo)

```ts
Client {
  customerNumber: number            // unique, allocated by Counter('customer') starting after max import
  name: string
  invoiceAddress: string            // multi-line
  domain?: string
  defaultPaymentTermDays: number    // default 30
  email?: string
  externalRefs?: { system: 'leagues.finance', associationId: string }[]
}

Invoice {
  invoiceNumber: string             // unique; new = YYYYMMDD-NN, legacy = any (flag legacy:true)
  legacy: boolean
  kind: 'invoice' | 'credit_note'
  cancels?: ObjectId                // credit_note → original invoice
  clientId: ObjectId; customerNumber: number   // denormalised for reference matching
  invoiceAddress: string            // snapshot at issue
  title: string                     // Sheet "invoiceName"
  invoiceDate?: Date                // set on markSent
  servicePeriod: string             // normalised MM.YYYY
  paymentTermDays: number; dueDate?: Date      // dueDate = invoiceDate + term, set on markSent
  currency: 'EUR'
  status: 'draft' | 'sent' | 'paid' | 'canceled'
  sentAt?, paidAt?, canceledAt?: Date
  totals: { netCents, vatCents, grossCents }   // recomputed from lines on every write
  payments: [{ bankTxId, amountCents, date, counterpartyIban?, reference }]
  reconcileState: 'unmatched' | 'partial' | 'matched' | 'overpaid'
  driveMetadata?: { fileId, folderId, link, fileName, filedAt, failureReason }
  source?: { system: 'leagues.finance', offerId?: string, seasonId?: number, associationId?: string }
  footerNotes?: string[]            // e.g. VAT-exemption legal text
}

InvoiceLine {
  invoiceId: ObjectId
  position: string                  // '1', '1.1'; sort by natural order
  description: string
  quantity: number                  // decimal allowed
  unitNetCents: number              // may be negative (discount line)
  vatRate: number                   // 0 | 0.07 | 0.16 | 0.19
  vatNote?: string
  source?: { leagueId?: number, chosenSource?: 'offer'|'live'|'custom' }   // leagues.finance passthrough
}
// line totals are derived, not stored

Counter { _id: 'customer' | 'invoice:YYYYMMDD', seq }   // atomic findOneAndUpdate($inc)

BankTransaction {                    // cache of Firefly deposits
  fireflyJournalId: string           // unique — idempotency key
  date, amountCents, currency, description, counterpartyName?, counterpartyIban?
  matchedInvoiceId?: ObjectId; matchMethod?: 'reference' | 'manual'
  ignored?: boolean                  // not an invoice payment (interest, refunds…)
}

ReconcileRun { startedAt, finishedAt, fetched, matched, partial, unmatched, error? }
```

**Invariants (enforced in a single `invoiceStateMachine.ts`, unit-tested):**
- Lines, title, address, period, term: editable only in `draft`.
- `markSent`: requires ≥1 line and gross ≠ 0, sets `invoiceDate` (default today), `dueDate`, snapshots `invoiceAddress`, triggers PDF + Drive filing.
- `sent → paid`: via reconcile (sum of payments ≥ gross) or manual `markPaid {paidAt, note}`.
- `sent → canceled`: only by issuing a credit note (`invoices.cancel {id, reason}` creates the credit note in `sent` state with negated lines and sets the original to `canceled`).
- `draft` may be deleted (its number was never issued; remaining numbers of the day stay unique, gaps in drafts are acceptable).
- `invoiceNumber`, `customerNumber`, `kind` immutable after creation.
- `overdue` = `status:'sent' && dueDate < startOfToday` (query: `{status:'sent', dueDate:{$lt: today}}`).

## App surface

**Routes:** `/dashboard /invoices /invoices/new /invoices/:id /invoices/:id/edit /clients /clients/:id /bank /reports /settings /login`.

**tRPC (`adminProcedure` unless noted):**
- `clients.{list,get,create,update}` (no delete once invoices exist; `archive` instead).
- `invoices.{list {status?, clientId?, overdueOnly?, year?, search?}, get, createDraft, updateDraft, setLines, deleteDraft, markSent, markPaid, cancel}`.
- `bank.{list {unmatchedOnly?}, assign {bankTxId, invoiceId}, unassign, ignore, syncNow}`; `reconcile.status` (last `ReconcileRun`).
- `reports.{openItems, revenueByYear, revenueByClient}` + `GET /api/export/invoices.csv` (Sheet-shaped columns for the tax advisor).
- **`ext.*` service API** for leagues.finance (Task 10): bearer service token, `ext.clients.upsertByExternalRef`, `ext.invoices.create` (returns number), `ext.invoices.get`.

**UI action visibility:** Edit/Lines/Delete/Mark sent = draft · Mark paid/Cancel (credit note)/Assign payment = sent · paid/canceled = read-only + payment history + link to credit note.

**UI display statuses (derived, never stored):** `status` stays `draft|sent|paid|canceled`; mocks (`docs/mocks/`) add derived badges — `überfällig` = `sent && dueDate < today`, `teilbezahlt` = `sent && payments.length > 0` (purple `b-part`), `Stornorechnung` = `kind: credit_note` (white/red `b-credit`) vs `storniert` = `status: canceled` (red). Filter chip `Storniert` matches `canceled OR kind: credit_note`. Badge colours: draft gray / sent blue / overdue amber / paid green / partial purple / canceled red / credit white-red.

### Task 7: Reconcile

**Create:** `lib/reconcile.ts`, `src/server/cron/reconcile.ts` (CLI entry: sync → match → write `ReconcileRun`, exit non-zero on error), `routers/reconcile.ts`.
**Matching rules:**
1. `parseReference(desc)`: tolerant regex `/(\d{5})\s*[-/ ]?\s*(\d{8})\s*[-/ ]?\s*(\d{2})/` (banks insert spaces/line breaks; strip whitespace first). Also accept bare `\d{8}-\d{2}`. Customer number must match the invoice's, else → unmatched.
2. Matched invoice must be `sent` (or `paid` → record as overpayment, flag).
3. Sum payments: `= gross` → `paid` + `paidAt = last payment date`; `< gross` → `partial`; `> gross` → `overpaid` (stays `paid`, flagged on dashboard).
4. Everything else → unmatched queue in `/bank`, where the UI suggests candidates (same amount ± 0, open invoices, counterparty name ≈ client name) for one-click `bank.assign`. Legacy invoices are only ever matched this way.
5. Idempotent: a `BankTransaction` with `matchedInvoiceId` is never re-applied; `bank.unassign` reverses payment + status.
**Tests:** exact → paid; two partials → paid on second run; overpaid flagged; re-run is a no-op; wrong customer number → unmatched; reference with spaces/newline parsed; credit-note invoices never matched.
Commit `feat: auto-reconcile by Verwendungszweck`.
